## 핵심 한 줄

> **분산락의 근본은 비관적 락이다.**
> DB의 `SELECT FOR UPDATE`와 원리는 같지만, 디스크(DB) 대신 메모리(Redis)에서 처리해 압도적으로 빠르다.

---

## Redis 분산락 = RDBMS 앞단의 프록시(전처리)

Redis가 RDBMS 앞에서 수만 명의 요청을 줄 세우고 입구 컷을 해준다.
덕분에 무겁고 소중한 DB는 딱 한 명씩만 상대하면 된다.

```
[수만 명의 요청]
       ↓
  [ Redis 분산락 ]  ← 프록시 / 전처리 레이어 (메모리, 초고속)
       ↓ (1명씩만 통과)
  [ RDBMS / MySQL ]  ← 실제 데이터 처리 (디스크, 안전)
```

---

## 일반 Redis 락 구조

Redis 서버 1대에 키값 하나를 선점하는 방식.

```
[서버 A] ──▶  [ Redis 서버 1대 ]  ◀── [서버 B]
               ( key: "coupon_lock" )
```

- 서버 A가 `coupon_lock` Key 선점 → **락 획득**
- 서버 B가 같은 Key 요청 → Redis 거절 → **대기**
- 서버 A가 Key 삭제 → **락 해제** → 서버 B 진입

| | DB 비관적 락 | Redis 분산락 |
| --- | --- | --- |
| 원리 | 먼저 온 놈이 선점, 나머지 대기 | 동일 |
| 처리 위치 | DB 내부 (디스크) | Redis (메모리) |
| 속도 | 느림 | 압도적으로 빠름 |

---

## 장애 시나리오

### 자바(앱) 서버가 죽는 경우 → 데드락

락을 쥔 채 서버 강제 종료 → `unlock()` 실행 불가 → 자물쇠 영구 잠금
→ 다른 서버들 영원히 대기 → **서비스 마비**

**해결:** 락에 **만료 시간(Lease Time)** 필수 설정 (예: 5초 뒤 자동 삭제)

### Redis 인프라가 죽는 경우 → 동시성 붕괴

락 검사 불가 → 여러 서버가 동시에 DB 수정
→ **재고 마이너스 등 데이터 꼬임**

**해결:** AWS ElastiCache 자동 Failover 등 안정적인 클라우드 인프라 구성

---

## 레드락(Redlock) — 오버엔지니어링

Redis 서버 **5대**에 과반수(3대) 동의 시 락 획득하는 방식.

| 단점 | 내용 |
| --- | --- |
| 비용 | 서버 5대 구매·관리·모니터링 |
| 성능 | 락마다 5대에 네트워크 요청 → 속도 저하 |
| 완벽하지 않음 | GC 멈춤·네트워크 지연으로 5대도 뚫림 |

**결론: 클라우드 인프라를 안정적으로 구성하는 게 훨씬 가성비 좋음**

## 실무 주의사항

### 함정 1: 트랜잭션과 락 해제 타이밍

```java
// ❌ 잘못된 코드 — unlock() 후 DB Commit 발생
lock.lock();
itemService.decrease(itemId);  // 트랜잭션 내부
lock.unlock();                 // Commit 전에 락이 먼저 풀림!
```

**올바른 순서:** `락 획득 → 트랜잭션 시작 → 로직 → Commit 완료 → 락 해제`
→ AOP 또는 파사드 패턴으로 락이 트랜잭션을 완전히 감싸도록 설계

### 함정 2: 만료 시간 < 작업 시간

락 만료 3초인데 작업이 4초 걸리면 → 락 강제 해제 → 동시성 붕괴

**해결 (Redisson Watchdog):** 작업 미완료 시 주기적으로 만료 시간 자동 연장
