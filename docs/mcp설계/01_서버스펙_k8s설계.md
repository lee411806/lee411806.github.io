---

## 쿠버네티스 선택: k3s

### 선택 이유

- 풀 k8s 컨트롤 플레인은 RAM 2-3GB 소모 → 8GB에서 빠듯함
- k3s는 약 512MB로 동작 → 워크로드에 여유 확보

### RAM 예상 배분

**k3s 사용 시 (현재 선택)**

| 용도 | 사용량 |
|------|--------|
| OS/시스템 | ~1GB |
| k3s 서버 | ~512MB |
| MCP 워크로드 | ~6GB (여유) |

**풀 Kubernetes 사용 시**

| 용도 | 사용량 |
|------|--------|
| OS/시스템 | ~1GB |
| k8s 컨트롤 플레인 (etcd, API서버 등) | ~2-3GB |
| MCP 워크로드 | ~4-5GB (빠듯함) |

→ MCP 워크로드가 실제 서비스 연동(DB, API 등)을 처리하는 영역이므로 여유가 클수록 안정적. 풀 k8s는 컨트롤 플레인이 RAM을 많이 잡아 워크로드가 빠듯해짐.

### k3s vs minikube

| | k3s | minikube |
|---|---|---|
| 목적 | 경량 프로덕션 | 로컬 개발/테스트 |
| 사용 환경 | 실제 서버 | 개발자 노트북 |
| 포트폴리오 가치 | 높음 | 낮음 |

→ VM 서버 환경이므로 **k3s 선택**

## 포트폴리오 관점

### k3s 선택 이유

- 풀 k8s는 멀티노드 클러스터에서 진가를 발휘하도록 설계된 범용 오케스트레이터
- 싱글노드에서는 컨트롤 플레인 오버헤드만 크고 멀티노드 이점을 살릴 수 없음
- k3s는 싱글노드/온프레미스 환경에 최적화되어 동일한 기능을 더 적은 리소스로 제공
- CNCF 공식 인증 배포판으로 풀 k8s와 동일한 API 사용 가능

## 현재 방식

- 싱글 노드 구성 (POC)
- 오케스트레이션 기능 활용 (Pod, Deployment, Service, ConfigMap 등)
- HA/멀티노드는 지원 안 되나 POC 목적으로 충분
